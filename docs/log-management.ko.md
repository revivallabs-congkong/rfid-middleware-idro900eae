# 로그 데이터 관리·용량 정책

> 로컬에 쌓이는 로그가 어떻게 회전·삭제되고 용량이 어디까지 커지는지.
> 코드: `internal/logging/logging.go`.

## 1. 저장 위치·형식

- 경로: `dataDir\logs\middleware-YYYYMMDD.jsonl`
- 형식: JSON Lines(한 줄에 이벤트 1개). 하루 한 파일이 기본이며, 파일이 커지면
  `middleware-YYYYMMDD.1.jsonl`, `.2.jsonl` 로 이어진다.

## 2. 회전(rotation) — 언제 새 파일로 넘어가나

로그를 쓸 때마다 검사해 셋 중 하나면 새 파일로 전환한다.

- 파일이 **10 MiB**(`rotateSize`)를 넘으려 할 때
- **날짜가 바뀔 때**(자정)
- 프로세스 재시작 시(기존 파일이 상한 미만이면 이어 쓴다)

## 3. 보관 상한(retention) — 오래된 파일 삭제

회전이 일어날 때마다 `cleanup()` 이 **두 기준을 함께** 적용한다.

- **14일**(`keepDays`)보다 오래된 날짜의 파일은 삭제
- 그러고도 파일이 **10개**(`keepFiles`)를 넘으면 오래된 것부터 삭제
- 삭제 실패는 조용히 무시하고 로깅은 계속된다(정리 실패가 서비스를 막지 않는다).

## 4. 최대 용량 — 사실상의 천장

**10 MiB × 10개 = 약 100 MiB** 가 로그 폴더의 상한이다. 14일 조건이 더 빡빡하면
그보다 작아진다. 어느 기기든 로그가 이 이상으로 디스크를 잠식하지 않는다.

## 5. 용량을 좌우하는 실질 변수 — `logLevel`

- `logLevel: "debug"` 이면 리더가 초당 수백~수천 건 보내는 `DEBOUNCE_DROP`·
  `READER_RAW` 가 전부 기록돼, 10 MiB 파일이 **몇 분~몇십 분** 만에 차서 회전이
  잦아진다. 총량은 여전히 100 MiB 상한이라 디스크는 안전하지만, 회전이 빨라
  **하루 이틀치 이력만** 남을 수 있다.
- **운영 권장값은 `info`.** 고빈도 로그가 빠지고 의미 있는 이벤트(체크인 결과·
  연결·경고)만 남아, 같은 100 MiB 로 훨씬 긴 기간을 보관한다.
- `debug` 는 현장 디버깅·마법사 관측 때만 한시적으로 쓰고 끝나면 `info` 로 되돌린다.
  (`DEBOUNCE_DROP` 이 왜 기기마다 다르게 쌓이는지는 정상 동작 — 리더 인식 빈도 차이.)

## 6. 회전 대상이 아닌 것

- **마법사 리포트**(`dataDir\reports\`)는 회전 대상이 아니다. 운영자가 명시적으로
  저장할 때만 생기고 개수가 적어 관리 부담이 없다. 불필요하면 수동 삭제.
- **`status.json`**(`dataDir` 루트)은 매번 덮어써지는 단일 파일이라 누적되지 않는다.

## 7. 상한값 조정

`rotateSize`(10 MiB)·`keepFiles`(10)·`keepDays`(14)는 현재 코드 상수다. 현장에서
더 길게/짧게 보관하려면 이 3개만 바꾸면 된다. 로그에는 참가자 PII·전체 토큰이
남지 않으므로(설계 §8.3, R8), 보관 기간 연장 자체에 개인정보 리스크는 없다.
