# 프로그램 다운 시 복구·조치

> 미들웨어(서비스 또는 GUI 호스팅)가 비정상 종료·크래시·강제 종료·정전으로
> 멈췄을 때, 자동으로 복구되는 것과 운영자가 해야 할 조치.
> 코드: `internal/winsvc/`, `internal/app/app.go`, `internal/store/sqlite/`.

## 1. 데이터는 잃지 않는다 — 자동 복구 3가지

미들웨어는 크래시를 전제로 설계돼 있다. 재기동하면 아래가 자동 복구된다.

### 1.1 큐(체크인 대기 기록) — SQLite durable
- 큐는 `dataDir\queue.db`에 **WAL 모드**로 즉시 기록된다. 스캔이 큐에 들어가는
  순간 디스크에 남으므로, 그 뒤 크래시가 나도 **적재된 기록은 보존**된다.
- 처리 중이던 행은 서버 응답을 받아 `Complete` 하기 전까지 **삭제되지 않는다**.
  따라서 "전송 도중 크래시"가 나도 다음 기동에서 원래 `checkedAt` 그대로 재전송된다
  (최대 24시간 만료 한도 내). 이중 전송은 서버 쿨다운이 409로 흡수한다.
- ⚠️ 한계: **아직 큐에 들어가지 않은 스캔**(리더가 읽었지만 적재 전 순간)은 복구
  대상이 아니다. RFID 리드는 재생 불가라 이건 원리상 어쩔 수 없다 — 그래서 무인
  장시간 운영은 창을 닫으면 죽는 GUI 가 아니라 **서비스 모드**가 기본이다.

### 1.2 게이트 상태 — 재시작을 넘어 유지
- 토큰 회수(`SUSPENDED_TOKEN`)·재바인딩(`SUSPENDED_REBIND`)·설정 이상
  (`SUSPENDED_CONFIG`) 같은 중단 상태는 영속화돼 **재기동 후에도 유지**된다
  (`GATE_RESTORED_SUSPENDED` 로그). 크래시로 중단이 풀려 잘못 전송되는 일이 없다.
- 복원된 suspension 은 preflight 로 자동 해제되지 않는다 — 운영자의 명시적
  재개(`queue resume` 또는 GUI [재개])가 필요하다.

### 1.3 Windows 서비스 — 자동 재시작
- `service install` 시 복구 정책이 함께 설정된다(`internal/winsvc`):
  **Automatic (Delayed Start)** + 실패 시 **1분 후 재시작 3회, 이후에도 재시작 유지**.
- 즉 서비스 프로세스가 죽어도 **최대 1분 내 SCM 이 자동 재기동**하고, 위 1.1·1.2 가
  복구된다. 노트북 재부팅 후에도 자동 시작된다.

## 2. 이중 기동 방지
- `dataDir\app.lock` 배타 잠금으로 **같은 dataDir 에 코어가 둘 이상 뜨지 못한다**.
  서비스가 도는 중 GUI 를 켜면 GUI 는 자동으로 관측(읽기 전용) 모드가 된다.
- GUI 프로세스 자체도 `gui.lock` 으로 단일 인스턴스만 유지된다(트레이 아이콘 1개).

## 3. 증상별 조치

### 3.1 서비스 모드 — 대부분 자동
1. 보통 아무것도 안 해도 1분 내 자동 재시작된다.
2. 상태 확인:
   - GUI 를 열면 대시보드 상단 **수집 인디케이터**로 판단(초록=수집 중).
   - 또는 명령: `rfid-middleware status --data-dir <dataDir>` → `updatedAt` 이
     현재 시각 근처면 정상. 15초 이상 과거면 코어가 멈춘 것.
   - `services.msc` 에서 **CongKong RFID Middleware** 가 "실행 중"인지.
3. 자동 재시작이 안 되면(설정 오류로 즉시 재크래시 등): 아래 3.3.

### 3.2 GUI 호스팅 모드 — 창을 닫았거나 프로세스가 죽음
1. exe 를 **다시 실행**(더블클릭)하면 호스팅 모드로 떠서 큐·게이트가 복구된다.
2. 재실행 시 "체크인 수집이 중지됨" 배지가 보이면 화면의 **[수집 시작]** 을 누른다
   (또는 트레이 종료 후 재실행).
3. 무인 운영 중이라면 이참에 **서비스 모드로 전환**을 권장:
   관리자 PowerShell 에서 `rfid-middleware.exe service install --config <path>` 후
   `service start`. 이후엔 3.1 처럼 자동 복구된다.

### 3.3 재시작해도 계속 죽을 때 (crash loop)
원인은 대개 **잘못된 설정**이다.
1. `rfid-middleware validate-config --config <path>` 로 설정을 검증한다.
   토큰 형식·리더 주소·dataDir 절대경로·PORT placeholder 등이 걸린다.
2. `dataDir\logs\middleware-*.jsonl` 마지막 줄에서 종료 직전 ERROR 를 확인한다.
3. 설정이 문제면 GUI [설정] 편집 또는 `config.json` 을 고친 뒤 다시 시작.
4. `dataDir` 쓰기 권한(디스크·ACL) 문제면 폴더 권한을 확인한다(설치 시 설치
   사용자에게 Modify 부여됨).

### 3.4 토큰 회수로 멈춘 뒤 재기동한 경우
- 재기동해도 해당 리더는 `SUSPENDED_TOKEN` 으로 남는다(의도된 동작).
- 새 토큰이 담긴 카탈로그를 받아 GUI 리더 카드의 **[새 토큰으로 재개]**, 또는
  서비스 중지 후 `rfid-middleware queue resume --reader <id> --pending send|discard`
  → 서비스 시작.

## 4. 크래시 후 점검 체크리스트
1. 수집 인디케이터 초록 / `status` 의 `updatedAt` 최신인지.
2. 각 리더 연결(초록)·게이트 상태 정상인지.
3. 대기 큐가 비정상적으로 쌓여 있지 않은지(인터넷·서버 확인).
4. 필요 시 **현장 점검 마법사** 0~2단계로 설정·리더·서버를 재확인.
5. 반복 크래시면 로그 마지막 ERROR 를 개발팀에 전달(토큰·PII 는 로그에 없음).
